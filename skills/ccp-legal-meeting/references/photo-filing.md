# 会后照片识别与归档

用户把会议照片（微信导出，文件名形如 `微信图片_20260915172432_124_15.jpg`）丢在当月根目录，需要识别内容、命名、归档，并压缩体积。

## 工作方式（用户 2026-09-17 最终确定）

> **不要在源图上直接猜归属就归档。分三步走：**
> 1. **先在源图片上改名**（不移动文件），格式 `会议照片【××××】9月<后缀>#`，`××××` = 主题党日/党员大会/支委会/党课，`<后缀>` = 图片识别出的内容，`#` = 该会议内序号。
> 2. **输出归档预案交给用户检查**，由用户核对识别成果并决定归入。
> 3. 用户**自己会动手删改**（删掉不要的、调整命名），改完再由 AI 核对命名是否正确 → 正确则**压缩 + 归档**。
>
> 用户原话："你把归档的照片全部删掉，然后在源图片上命名……然后由用户检查识别成果，并给出归档预案，再由用户决定归入。"
> 后续："我改了一下，帮我看看命名是否正确，不正确就提出，正确可以压缩大小、归档，并写入skill。"

**归档口径（2026-09-17 用户明确修订）**：
- **不删用户照片**：源图保留原位，归档用复制方式；另存一份备份到 `_bak_src\`。
- **取消"一项一张"规则**：按现有照片全部归档，不再按同页重拍去重（此前的"每项1张"口径已作废）。
- **保留序号**：归档到会议文件夹时文件名保留序号前缀。

## 第一原则：屏幕内容必须能与会议通知议程对应

**先把四份会议通知读出来**（`1.会议通知*/关于召开…的通知.docx`），列出各会议「四、会议内容/会议主题」的议程条目，作为识别基准。逐张看照片屏幕内容，找它在通知议程里的出处。**对应不上的一律标出来问用户，不擅自归属。**

### 判据优先级

1. **屏幕标题写明会议名称**（`党支部 9月支委会/9月主题党日/第三季度党课`）→ 直接归属。
2. **屏幕标题是某项学习内容** → 查该内容出现在哪份通知的议程里，归入该会议。
3. **人数与座位量级**（辅助参考，**不足以推翻屏幕证据**）：3 人围坐 = 支委会；长桌坐满 = 主题党日/党员大会/党课。
4. **屏幕优先于人数**：用户 2026-09-17 明确纠正——某张照片屏幕写「9月支委会」但现场坐了 11 人，**仍按屏幕归支委会**，不能用"人多"去推翻屏幕。**屏幕内容是第一证据。**

### 必须放大裁切细看屏幕（用户纠正："注意留意图片细节"）

照片整图缩略看极易误判，**必须把屏幕区域裁出来放大 2–5 倍再看一遍**（Pillow `crop` + `resize`，必要时加对比度）。踩过的三个坑：

- **①裁剪位置猜错 → 把大屏当成笔记本**。样例 124/125：首轮裁在画面左下角，看到的是前排人的**笔记本电脑**，误判为"无主题的现场照"；换成正确区域（`int(w*0.36), int(h*0.25), int(w*0.68), int(h*0.48)`）放大后，清晰可见大屏标题是党员大会的两份学习文件（「习近平作出重要指示强调 巩固拓展树立和践行正确政绩观学习教育成果…」「学习贯彻总书记重要指示精神 传达学习上级有关会议精神辅导讲稿」）。**裁错了区域比不裁更危险。**
- **②只看场景装饰会误判归属**。样例 129：整图看在"学习教育总结会"场景，误归党员大会；放大后屏幕实为**党课《习近平党建文选》第一卷、第二卷 2012年时间轴**（左上红标签"党建文选"）→ 归**党课**。
- **③同会议不同 PPT 页要分开命名**。党课 PPT 第1页=封面《习近平党建文选》、第8页=2012年时间轴，同属党课但内容页不同，命名要区分（后缀可加"（2012年）"）。

**裁切建议**：会议室大屏一般在画面**中上部**（约 x:0.32–0.72、y:0.20–0.48，视机型微调），先裁一张试看，位置不对再调，**不要一次批量裁完就用**。

## 改名格式与序号

`会议照片【{会议}】9月{内容描述}{序号}.jpg`

- 序号在**每个会议组内从 1 连续编**（不是全局编号）。
- 组内排序按会议流程：标题页 → 各项学习内容（按通知议程顺序）。
- **重编号必须两阶段**：先全部改成临时名（如 `__t{random}.jpg`），再改成目标名。直接原地改名会因目标名已存在而 `FileExistsError`（踩坑）。同时**去掉旧尾号时用 `re.sub(r"\d+$", "", body)`**，注意别把内容里的年份数字误删（"第一卷、第二卷"不含阿拉伯数字结尾，安全）。

## 归档预案（交用户决策）

改名后写一份 `_归档预案.md` 放当月根目录，内容包含：

1. **识别结果表**：按会议分组，逐张列「现文件名 | 屏幕内容」。
2. **归档预案**：每个会议的归档建议、目标文件夹路径。
3. **需用户决策事项**：对应不上通知议程的（如某张业务分享）、序号是否保留、是否压缩等。

## 核对用户改后的命名（用户会自己动手改）

用户拿到预案后通常会**自己删减、改文件名**。AI 收到"帮我看看命名是否正确"时要：

1. **用文件哈希查重**（`hashlib.md5`），确认没有同内容文件被重复保留。
2. **逐张裁切放大屏幕**，核对文件名描述与屏幕实际内容是否相符。
3. **检查序号规范性**：组内是否连续、有无漏序号。
4. **指出瑕疵但不擅自改**：明显与屏幕不符的要指出；只是命名详略不一的（如"学习《求是》…《坚持落实管党治党政治责任》"与"学习坚持落实管党治党政治责任"，实为同一文章的不同照片），提示可统一但不强制。
5. 用户确认后**才执行压缩 + 归档**。

## 压缩至 250KB 以内且保画质（用户要求）

```python
from io import BytesIO
from PIL import Image, ImageOps

LIMIT = 250 * 1024

def encode(img, q):
    buf = BytesIO()
    img.save(buf, "JPEG", quality=q, optimize=True, progressive=True, subsampling=0)
    return buf.getvalue()

def compress(img):
    orig = ImageOps.exif_transpose(img)
    if orig.mode in ("RGBA", "LA", "P"):
        bg = Image.new("RGB", orig.size, (255, 255, 255))
        c = orig.convert("RGBA"); bg.paste(c, mask=c.split()[-1]); orig = bg
    elif orig.mode != "RGB":
        orig = orig.convert("RGB")
    lo, hi, best = 40, 96, None
    for _ in range(6):                       # 二分法找满足限额的最高质量
        mid = (lo + hi) // 2
        data = encode(orig, mid)
        if len(data) <= LIMIT: best = (data, mid, orig.size); lo = mid + 1
        else: hi = mid - 1
    if best: return best
    # 质量 40 仍超才按面积比例缩尺寸（本场景用不到）
    ...
```

- **subsampling=0（4:4:4）** 色度不降采样，屏幕文字更锐利 —— 保画质关键；配合 `optimize` + `progressive`。
- 本场景 3–4MB / 约1300×1000 原图 **q88 即达标**（实测 127–228KB），**分辨率完全不缩**。
- **别写"每张循环试 8 档质量 × 多档尺寸"**：单张编码几十次，300万像素图极慢，进程会被 SIGTERM 杀掉。

## 操作要点

1. **先备份再改名**：原图先 `shutil.copy2` 到 `_bak_src\`，再在源图上改名。
2. **不删用户照片**：用户明确要求"不要删我的照片"。归档用**复制**（源图保留原位），除非用户另说。
3. **不确定先问**：对应不上通知议程的、序号是否保留、是否压缩 —— 用 AskUserQuestion 问用户。
4. **脚本结果写 txt 报告文件再 Read**：部分 shell 环境看不到 stdout（工具只回 exit code），否则无法确认执行结果。
5. **Windows 路径中文**：Git Bash 里 `ls`/`find`/`cp` 默认不可用，先 `export PATH="/usr/bin:/bin:/c/Windows/System32:/c/Users/ACME/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin"`；能用 Glob/Read 工具时优先用工具。
6. **清理临时目录**：裁切图、脚本等临时文件用完删掉，不要留在用户目录里。
